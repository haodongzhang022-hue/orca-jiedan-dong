## 二、差距分析（AS-IS vs TO-BE）

### 2.1 六实例完整性差距

| 实例 | 目标 | 当前状态 | 差距 |
|------|------|----------|------|
| **Hermes 桌面版** | 原生桌面应用，独立进程 | ⚠️ 运行时存在但桌面版未安装 | **需安装 Hermes-Setup.exe** |
| **Hermes CLI (可莉)** | 独立CLI进程，可被调度 | ✅ 当前Hermes Agent Session就是 | 已满足，需封装为可调度CLI |
| **Codex 桌面版** | 原生桌面应用 | ✅ codex-plus-plus.exe 已安装 | 需要建立与msgbus的桥接 |
| **Codex CLI** | 独立CLI进程 | ⚠️ 存在但频繁超时/skill加载失败 | **需修复稳定性** |
| **Claude 桌面版** | 原生桌面应用 | ✅ claude.exe 已安装 | 需要建立与msgbus的桥接 |
| **Claude CLI** | 独立CLI进程 | ✅ claude -p 正常工作 | 已满足 |

### 2.2 通信架构差距

| 能力 | 目标 | 当前 | 差距 |
|------|------|------|------|
| **桌面间通信** | Hermes↔Codex↔Claude 桌面版直接通信 | ❌ 无直接通信协议 | **需要新建IPC/HTTP桥接** |
| **CLI间通信** | CLI实例间直接通信 | ⚠️ 通过msgbus文件轮询（5s延迟） | 需升级为实时通信 |
| **桌面↔CLI切换** | 同一Agent的桌面版和CLI版可无缝切换 | ⚠️ msgbus有context快照但无真正切换 | 需实现状态同步机制 |
| **消息协议** | 统一高效的消息协议 | 文件JSON轮询（OMF v1.0） | **需升级为HTTP/WebSocket** |

### 2.3 角色分工差距

| 角色 | 目标 | 当前 | 差距 |
|------|------|------|------|
| **Hermes（大脑）** | 决策、任务分发、调度 | ✅ 已实现（Hermes Agent + autopilot） | 需增强为双入口统一调度 |
| **Codex（执行）** | 代码执行、物料生成 | ⚠️ CLI不稳定，桌面版未接入msgbus | **核心差距：需稳定CLI+桥接桌面** |
| **Claude（审查）** | 质量审查、合规检查 | ✅ CLI工作正常 | 需桥接桌面版 |

### 2.4 关键技术债

1. **msgbus消息风暴**：已修复根因（多实例+无限循环+去重缺陷），但文件轮询架构本质脆弱
2. **Codex CLI超时**：120s超时频繁触发，skill加载失败（路径指向G盘不存在的目录）
3. **Hermes桌面版未安装**：Hermes-Setup.exe已下载但未执行
4. **GUI是自搭HTTP服务器**：非原生桌面应用，而是Python HTTP + Edge --app= 模式
5. **端口冲突**：57365-57367在Windows动态端口保留区，绑定报WinError 10013

### 3.3 消息流示例

**场景：企业微信群收到一个海报设计需求**

```
用户 → 企业微信群 → [Webhook/Hermes Desktop]
                        │
                        ▼
  ┌─ Hermes Desktop ──────────────────────────┐
  │ 1. 解析需求 → task_id                     │
  │ 2. 生成 design_brief.md                   │
  │ 3. 写入 fleet_exchange/incoming/           │
  │ 4. 通过 msgbus 发送给 Codex               │
  └───────────────┬───────────────────────────┘
                  │ msgbus/HTTP
                  ▼
  ┌─ Codex Desktop 或 CLI ────────────────────┐
  │ 1. 认领任务（fleet_exchange/doing/）       │
  │ 2. 生成设计方案 + SVG + image_gen_req.json │
  │ 3. 写入 G盘 outputs/task_id/              │
  │ 4. 通过 msgbus 发送给 Claude               │

  └───────────────┬───────────────────────────┘

  ┌─ Hermes 汇总 ────────────────────────────┐
```

### 5.4 推荐方案

**务实路线**：在现有msgbus文件轮询基础上，为每个桌面版添加一个轻量HTTP桥接层，实现"桌面版能收发msgbus消息"。不追求实时WebSocket，不追求原生IPC，保持架构简单可维护。

```
桌面版 ──HTTP POST──→ bridge_adapter.py ──写文件──→ msgbus/inbox/
msgbus/inbox/ ──轮询──→ bridge_adapter.py ──HTTP推送──→ 桌面版
```

## 六、风险和注意事项

### 6.1 技术风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| **消息风暴复发** | 🔴 高 | 保持单实例锁+复合键去重，新增HTTP通道也加去重 |
| **6实例资源耗尽** | 🟡 中 | 监控内存/CPU，按需启停（不必6个全开） |
| **Codex CLI持续超时** | 🟡 中 | 增大超时到300s，添加重试，清理无效skill路径 |
| **桌面版API不兼容** | 🟡 中 | 降级为文件消息（桌面版轮询msgbus目录） |
| **端口冲突** | 🟡 中 | 避开端口保留区(49152-65535)，统一用15xxx段 |
| **Windows权限问题** | 🟢 低 | 已知WinError 10013，避开动态端口区即可 |

### 6.2 运维风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| **进程孤儿** | 🟡 中 | tui_gateway托管+lock文件+PID检测（已有） |
| **日志膨胀** | 🟢 低 | 日志写G盘，定期清理（retention_days=7） |
| **G盘空间不足** | 🟢 低 | outputs有回退到E盘机制（已有） |
| **升级困难** | 🟡 中 | 保持向后兼容，新旧版本可共存 |

### 6.3 架构注意事项

1. **不要过度工程化**：当前msgbus文件轮询虽简单但可靠，升级HTTP是锦上添花而非必须
2. **按需启动6实例**：不需要6个全开，根据任务类型选择性启动（简单任务只需Hermes+Codex）
3. **保持单Agent双入口的本质**：桌面版和CLI版是同一Agent的两个界面，不是两个独立Agent
4. **Hermes是唯一决策者**：无论桌面还是CLI，Hermes始终是大脑；Codex和Claude是执行/审查
5. **向后兼容**：旧的fleet_exchange文件流和msgbus文件消息必须继续工作
6. **避免C盘写入**：所有运行时数据写E盘（项目）或G盘（缓存），不碰C盘

### 6.4 关于"桌面版"的澄清

当前项目的"桌面版"有两种含义，需要区分：

| 含义 | 实例 | 说明 |
|------|------|------|
| **原生桌面应用** | Hermes Desktop, Codex Desktop, Claude Desktop | 厂商提供的独立程序，有GUI窗口 |
| **Fleet GUI（自搭）** | hermes_gui :15800, codex_gui :15801, claude_gui :15802 | Python HTTP服务器+Edge --app= 模式 |

用户愿景中的"桌面版"指的是**原生桌面应用**，而非自搭的Fleet GUI。Fleet GUI可以作为原生桌面应用不可用时的降级方案。
