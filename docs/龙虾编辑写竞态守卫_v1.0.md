## 一、它解决什么：「假成功」第 6 形态

**症状**
- 对**同一个文件**连续/并行发多个编辑调用
- 工具**全部返回 success**，回读却发现**部分改动没落盘**
- 或某个报 `EBUSY: resource busy or locked`，且**不会自动重试**

**根因**：编辑是 read-modify-write 三步、非原子。多写者并发时后写的基于旧副本覆盖先写的（静默丢失），或抢锁失败（显式 EBUSY）。两种都不崩、不报错，在自动化里最容易被当成「已完成」。

**实证（2026-09-16 受控实验）**

| 实验 | 结果 |
|---|---|
| 同一文件并行发 4 个编辑 | 1 个 `EBUSY` 失败（`version` 未改成），3 个成功 |
| 改用 edit_guard 一次原子应用 4 处 | **4/4 全落地**，回读断言全通过，EXIT=0 |
| patch 中故意放 1 条不匹配的 old | **拒绝写盘**，原文件 sha256 未变，EXIT=1 |
| 对已丢改动的文件跑 verify | 检出 `new_present: false`，EXIT=1 |

## 二、铁律

1. **同一文件多处修改，必须串行单发，发完 Read 回读核实。**
2. **更优解：不用多次编辑，改用 `edit_guard.py apply --patch patch.json` 一次搞定。**
3. 凡「改完就说完成」的动作，**必须有回读断言**，不能只看工具返回值。
4. 写前必备份（`--no-backup` 仅在确认可丢时用）。
5. `old` 必须与磁盘逐字节一致（空格/换行/全半角），否则在内存阶段就被拦下。

## 三、用法

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/versions/3.13.12/python.exe"
GUARD="G:/WorkBuddy_Data/skills/lobster-edit-race-guard/scripts/edit_guard.py"

"$PY" "$GUARD" apply  <file> --patch patch.json   # 原子应用多处修改
"$PY" "$GUARD" verify <file> --patch patch.json   # 只回读校验（不写盘）
"$PY" "$GUARD" fingerprint <file>                 # sha256/行数/编码/换行
"$PY" "$GUARD" locktest <file>                    # 探测文件是否被占用
```

### patch.json

```json
{
  "edits": [
    {"old": "version: 0.0.0", "new": "version: 1.0.0"},
    {"old": "alpha: AAAA",    "new": "alpha: ALPHA", "count": 1}
  ],
  "assert_old_absent": true
}
```

- `count`：期望替换次数，默认 1；**0 = 替换所有**
- `assert_old_absent`：默认 true，断言 old 已消失

### 开关与退出码

| 开关 | 作用 |
|---|---|
| `--no-backup` | 不建 `.bak_时间戳` |
| `--force` | 被占用时仍强制 `os.replace` |
| `--partial` | 允许部分未匹配也写盘（默认拒绝，保护原文件） |
| `--report <path>` | JSON 报告落盘供自动化判定 |

退出码：`0` 全通过 / `1` 有断言未通过（改动没落地）/ `2` 用法或文件错误。

## 四、为什么不丢改动

1. **单次落盘**：全部替换在内存完成，只 write 一次 → 根除竞态
2. **原子替换**：同目录临时文件 + `os.replace()`（Windows 原子）
3. **写前锁探测**：`os.open(O_RDWR)` 探 5 次，被占用先报不硬撞
4. **回读逐项断言**：写后重读，逐条校验 `new` 在、`old` 不在
5. **编码/换行保持**：自动识别 utf-8-sig / utf-8 / gbk 与 CRLF/LF 并原样写回
   —— 顺带防住「编辑工具把 LF 悄悄改成 CRLF」的换行漂移

## 五、边界

- 改动互相依赖时，patch 里的 `old` 要写**磁盘原文**，不是中间态
- 超大文件（>100MB）全量读写偏慢，改流式
- 二进制文件不适用
