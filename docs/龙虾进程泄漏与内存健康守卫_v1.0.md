## 一、为什么需要它

本机反复卡顿，排查了两轮：

- **第一轮的误判**：先怀疑 G 盘（Seagate USB 外置盘）掉盘 —— Event 153 逻辑块重试确实爆发，Python 直报「无法访问 `python313.dll`：磁盘丢失」。看起来根因找到了。
- **17:11 反转**：G 盘风暴已停（60 分钟内 0 次 Event 153、读取 1ms），机器**依然卡**。
- **真凶**：进程泄漏堆积把内存压到 **90%**。

| 进程 | 实例数 | 占用 |
|---|---|---|
| GptBrowser.exe | 78 | 11.88 GB（单进程最高 4.5 GB） |
| WorkBuddy.exe | 18 | 2.76 GB |
| 物理内存 | — | 28.6 / 31.7 GB ≈ 90% |

根因找到了，却没有工具化 —— 下次还得重查一遍。本守卫把这个洞补上。

**教训**：现象相同（界面卡死），根因可以完全不同。必须先量化再下结论，
不能因为上一轮刚抓到一个可疑项就把它当定论。

## 三、快速使用

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/versions/3.13.12/python.exe"
S="E:/龙虾AI主控中心/我的AI分身/企业微信群定制接单项目/scripts/lobster_mem_guard.py"

"$PY" "$S"                      # 体检报告（默认，只读）
"$PY" "$S" --json               # 机器可读，接 guard_receipt
"$PY" "$S" --plan               # 生成清理 bat（不执行）
"$PY" "$S" --trend              # 只看历史趋势
"$PY" "$S" --watch 5 --interval 60   # 采样 5 次判泄漏累积
"$PY" "$S" --apply --i-know-what-i-am-doing   # 真清理（双保险）
```

退出码：`0`=绿/黄，`1`=红（可接告警），`2`=采集失败，`3`=安全闸门拒绝。

## 四、判级规则

**内存**：占用率 ≥90% 或 可用 ≤2GB → 红；≥80% 或 可用 ≤4GB → 黄；否则绿。

**进程实例数**（每进程可配 `yellow / red / keep / killable`）：

| 进程 | 黄 | 红 | 清理保留 | 可杀 |
|---|---|---|---|---|
| GptBrowser.exe | 12 | 30 | 3 | 是 |
| 360se.exe | 8 | 20 | 2 | 是 |
| Doubao.exe | 8 | 18 | 2 | 是 |
| chrome.exe / msedge.exe | 15 / 12 | 40 / 30 | 3 / 2 | 是 |
| WorkBuddy.exe | 12 | 25 | — | **否（宿主自身）** |
| python / pythonw / node | 10 | 25 | — | **否（MCP 服务）** |
| 未登记进程 | 15 | 40 | — | 否（只观察） |

**单进程巨兽**：≥1.5 GB 点名，≥3 GB 判红。

## 五、三条安全红线

1. **默认只读**。`--apply` 才动手，且必须再叠 `--i-know-what-i-am-doing`，否则硬拒绝（exit 3）。
2. **白名单永不杀**：`WorkBuddy / python / pythonw / node / bash / git / ssh / explorer / svchost / csrss / lsass …`
   杀宿主 = 自杀式打断会话。
3. **保留策略**：按内存降序保留 Top-`keep` 个（视为主窗口 / 在用标签页），其余判为重复或僵尸。
   ⚠️ 这是启发式不是保证 —— 首次使用务必先 `--plan` 人工核对 PID 清单。

## 六、系统噪声豁免（防误报）

`svchost.exe / conhost.exe / RuntimeBroker.exe / dllhost.exe / WUDFHost.exe / taskhostw.exe / MsMpEng.exe …`
**天生多实例，一律强制判绿、不参与总评**。

> **踩坑实录**：v1.0 初版把 `svchost.exe` 81 实例判成红，导致总评永远红。
> **守卫一旦误报就没人信了** —— 噪声豁免是守卫可信度的生命线。

## 七、本次开发踩坑与修复

| # | 坑 | 修法 |
|---|---|---|
| 1 | 系统进程多实例 → 误报红 | `SYSTEM_NOISE` 集合强制判绿 |
| 2 | bat 行尾被文本模式二次转换 → 实际落盘 `\r\r\n` | `open(..., newline="\r\n")` + `"\n".join()` |
| 3 | bat 注释含中文 → GBK 控制台乱码 / 静默失效 | bat 全 ASCII 输出 |
| 4 | 演示 bat 含 71 条真实 `taskkill` PID | 用完立即删除，禁止留在 `backups/` |

第 2、3 条正是「假成功第 1 形态」（bat 编码/行尾错导致静默失败）的新实例：
**脚本生成成功 ≠ 脚本能跑**。凡生成 .bat 一律 ASCII + 精确 CRLF，并回读字节校验。
