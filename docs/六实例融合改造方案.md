## 交付物 ①  双架构融合差异对照表

### 1.1 架构对比概览

| 维度 | 现有双实例架构（AS-IS） | 目标六实例双入口（TO-BE） | 判定 |
|------|------------------------|--------------------------|------|
| 实例数量 | 3 Agent × 1入口 ≈ 3进程 | 3 Agent × 2入口 = 6进程 | **新增** |
| 桌面版 | Hermes未安装；Codex/Claude已装但未接入msgbus | 三个桌面版全部接入msgbus | **改造+新建** |
| CLI版 | Hermes CLI活跃；Codex CLI不稳定；Claude CLI正常 | 三个CLI全部稳定可调度 | **改造** |
| 通信层 | 文件JSON轮询（5s），6窗口已有 | 文件轮询 + HTTP桥接双通道 | **新增HTTP层** |
| 调度脚本 | launch_all_dual_instance.cmd（4步启动） | launch_all_six_instances.cmd（6步启动） | **改造** |

### 1.2 逐模块分类

#### ✅ 共用模块（可直接复用，零改动）

| 模块 | 路径/端口 | 复用理由 |
|------|-----------|----------|
| msgbus 目录结构 | `msgbus/inbox/{6窗口}/` | 6个窗口名已在registry.json注册，目录实际已存在 |
| msgbus_router.py 核心路由逻辑 | `scripts/msgbus_router.py` | chain转发、复合键去重、单实例锁均可用 |
| msgbus_agent_consumer.py 消费框架 | `scripts/msgbus_agent_consumer.py` | claude/codex CLI调用逻辑不变 |
| pipeline_autopilot.py 流水线 | `scripts/pipeline_autopilot.py` | fleet_exchange任务推进逻辑不变 |
| fleet_exchange 任务队列 | `fleet_exchange/incoming/doing/done/results/` | 与通信层无关，纯文件流 |
| aicodeswitch 模型路由 | `:4567` | 共享基础设施，与实例数无关 |
| context快照同步 | `msgbus/context/{agent}_context.json` | 已有3个context，双入口共享同一文件即可 |
| 稳定性监控 | `scripts/stability_monitor.py` | 只需追加新端口到PORTS字典 |
| 业务技能集 | skills/目录 | 与实例数无关 |

#### ⚠️ 冲突模块（需改造才能兼容六实例）

| 模块 | 当前状态 | 冲突点 | 改造方案 |
|------|----------|--------|----------|
| **launch_all_dual_instance.cmd** | 只启动4个进程（Codex GUI + Hermes CLI + Claude Serve + 报告） | 不含Hermes Desktop、Claude Desktop、Codex CLI | 拆分为两步：①保留现有脚本不动；②新建launch_all_six_instances.cmd覆盖全部6个 |
| **msgbus_agent_consumer.py** | codex超时120s，无hermes消费者 | ①codex timeout太短；②缺hermes CLI消费者 | ①timeout改为300s；②按需新增hermes消费者（非必须，Hermes CLI不走consumer） |
| **registry.json 端口分配** | gui_panel端口57365-57367落在Windows动态端口保留区 | 绑定报WinError 10013 | 迁移到15800/15801/15802段（实际运行已用15800/15801/15802，registry字段需同步） |
| **stability_monitor.py** | PORTS只监测3个端口 | 六实例需监测6+端口 | 扩展PORTS字典 |
| **Codex CLI调用参数** | `codex exec --skip-git-repo-check`，timeout=120s | 超时频繁、skill加载失败（G盘路径不存在） | ①timeout=300s；②清理codex skill路径；③增加重试机制 |

#### 🆕 新增模块（需全新开发）

| 模块 | 用途 | 预估工作量 | 依赖关系 |
|------|------|-----------|----------|
| **bridge_adapter.py** | 桌面版↔msgbus HTTP桥接适配器 | 4h | 无 |
| **msgbus_http_api.py** | 给msgbus加HTTP接口（/api/send, /api/poll） | 3h | 依赖bridge_adapter架构 |
| **context_sync.py** | 桌面版↔CLI版 context双向同步 | 1.5h | 依赖msgbus context目录 |
| **launch_all_six_instances.cmd** | 一键启动6个实例 | 30min | 依赖各实例稳定性 |
| **desktop_bridge_hermes.py** | Hermes桌面版HTTP注入 | 1h | 需先安装Hermes桌面版 |
| **desktop_bridge_codex.py** | Codex桌面版消息轮询钩子 | 1.5h | 需确认codex-plus-plus.exe是否暴露API |
| **desktop_bridge_claude.py** | Claude桌面版消息接收（利用claude serve） | 1h | 依赖claude serve :57330 |

### 1.3 融合可行性判断

| 判断维度 | 结论 | 说明 |
|----------|------|------|
| **共用模块占比** | ~65% | msgbus核心、fleet_exchange、pipeline_autopilot、aicodeswitch全部可复用 |
| **冲突模块改造量** | ~20% | 主要是端口配置和超时参数的配置级改动，不涉及架构重写 |
| **新增模块工作量** | ~15% | 桥接层是唯一需要全新开发的部分 |
| **融合方式** | **平滑兼容 ✅** | 不需要二选一。六实例架构是双实例的超集——原有launch_all_dual_instance.cmd继续工作，新增的六实例脚本在之上叠加。msgbus文件层完全向后兼容。 |

**核心结论**：双实例→六实例是**渐进式扩展**，不是破坏性重构。改造期间现有商单流水线零中断。

## 交付物 ③  桥接层简化替代方案

### 3.1 "桌面HTTP桥接层"刚需评估

| 评估维度 | 分析 | 结论 |
|----------|------|------|
| **核心需求** | 桌面版（原生程序）需要能收发msgbus消息 | 确实需要某种桥梁 |
| **HTTP是否唯一方案** | 否。桌面版本身不提供HTTP API，HTTP桥是我们自己加的中间层 | HTTP是**充分条件**而非**必要条件** |
| **已有可用通道** | Claude Desktop有`claude serve`（HTTP API）；Codex Desktop不确定是否有API | 部分可用 |

### 3.2 三种方案对比

#### 方案A：完整HTTP桥接层（原文方案）

```
桌面版 ←→ bridge_adapter.py(15900) ←→ msgbus/inbox/*.json
```

| 优点 | 缺点 |
|------|------|
| 统一架构，所有桌面版同一模式 | 开发量大（3个bridge + 1个HTTP API） |
| 可扩展性好 | 需要维护额外的HTTP服务进程 |
| 支持实时推送（WebSocket） | 过度工程化：当前实际只有1-2个桌面版在用 |

#### 方案B：文件夹观察者方案（推荐★）

```
桌面版(或其wrapper脚本) 直接轮询 msgbus/inbox/{agent}_gui/ 目录
```

| 优点 | 缺点 |
|------|------|
| **零新增代码**：复用msgbus已有的文件轮询机制 | 轮询延迟（但5s已可接受） |
| 不需要额外HTTP服务 | 桌面版需要一个轮询wrapper |
| 与CLI消费者架构完全对称 | 不支持实时推送 |
| 故障排查简单：直接看文件系统 | |

**实现方式**：为每个桌面版写一个轻量wrapper脚本（50行Python），功能等同msgbus_agent_consumer.py但是针对桌面版的：
- 轮询 `msgbus/inbox/{agent}_gui/`
- 收到消息后通过桌面版的原生注入方式推送（Claude用`claude -p`，Hermes用HTTP API，Codex写临时文件）
- 处理结果写回msgbus

#### 方案C：混合方案（务实推荐）

| 桌面版 | 通信方式 | 理由 |
|--------|----------|------|
| Hermes Desktop | HTTP桥接（已有gui_server.py :15800） | 已有HTTP端点，加/api/msgbus即可 |
| Codex Desktop | 文件夹观察者 | 不确定codex-plus-plus.exe是否有API，降级为文件轮询 |
| Claude Desktop | claude serve直连（:57330） | Claude原生支持HTTP API，不需要额外桥接 |

### 3.3 推荐方案：方案C（混合方案）

**理由**：
1. Hermes桌面版的gui_server.py（:15800）已经是HTTP服务器，只需在上面加/msgbus相关端点 → 1h
2. Claude Desktop有`claude serve :57330`原生API → 直接用，0开发
3. Codex Desktop不确定性最大 → 用文件夹观察者兜底 → 1h

**总开发量**：2h（vs 原方案8-10h），降低80%复杂度

**验证标准**：
- Hermes桌面版通过 :15800/api/send 收发消息 → curl测试
- Claude桌面版通过 :57330 API处理消息 → 端到端测试
- Codex桌面版通过文件轮询收到消息 → 检查codex_gui/目录消费日志
