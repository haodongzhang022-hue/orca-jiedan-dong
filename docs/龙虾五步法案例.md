# 龙虾五步法案例：企业微信群定制接单项目

## 案例名称
建设「网盘课程资源知识萃取与沉淀体系」项目，实现课程资源自动萃取 → 结构化沉淀 → 商单变现。

## 案例背景
用户积累了多份网盘付费课程资源，希望：
1. 不下载大体积视频，只萃取核心知识与 SOP；
2. 沉淀到 Obsidian 双知识库；
3. 形成可复用技能，后续多 Agent 舰队可自动执行；
4. 最终输出可商单交付的笔记/思维导图/培训方案。

## 龙虾五步法执行实录

### Step 1 精准备份
- 操作：扫描课程目录结构，生成 `source_manifest.json` 备份清单，不复制大文件。
- 原则：不修改任何原始课程文件，只读取目录与文件名信息。
- 产物：`backups/<timestamp>/source_manifest.json`

### Step 2 根因诊断
- 操作：识别资源类型（视频 / PDF / Word / 文本 / 音频），统计文件数与大小，估算处理时长。
- 判断：文本类文件可完整读取；视频/音频依赖本地 ffmpeg + whisper；模型后端默认 Ollama。
- 产物：日志中的扫描结果与资源类型分布

### Step 3 无命令不执行
- 操作：按 `config/default_config.yaml` 与 `config/model_config.yaml` 执行萃取；
  - 文本分段 → 模型摘要 → 知识点提取 → 模板渲染 → 知识库同步。
- 授权：首次访问新目录、涉及大量文件操作、同步外部平台前询问用户。
- 产物：`outputs/` 下的大纲、知识卡片、思维导图、商单交付物

### Step 4 验证修复
- 操作：抽检输出文件是否生成、关键字段是否非空、知识卡片数量是否达标。
- 标准：萃取准确率 ≥ 90%、知识点覆盖率 ≥ 85%。
- 降级：模型不可用时自动回退 mock，记录日志提示用户配置模型。

### Step 5 沉淀归档
- 操作：
  1. 写入 Obsidian 主库（`E:/.../副业项目库`）与备份库（`G:/...`）
  2. 更新 `skill_registry.json` 注册本技能案例
  3. 生成 `docs/技能沉淀/知识萃取技能.md` 技能卡片
  4. 项目文件提交到 Git 仓库，并同步到 GitHub 私有仓库（后续配置）
- 产物：技能卡片、商单交付模板、Git 提交记录

## 经验复用
- 同样流程可用于企业内部培训课程、行业研报、播客节目等知识源。
- 只需替换输入目录与课程分类标签，萃取引擎与模板即可复用。
- 多 Agent 舰队可调用 `scripts/auto_knowledge_extract.py`，实现自动化流水线。

## 风险与合规
- 不破解、不传播付费课程原文件。
- 知识萃取仅用于个人学习与商业笔记输出，不涉及版权侵权。

## 案例二：多代理稳定性修复（2026-07-29）

### 案例名称
修复 Codex 桌面版 401 Unauthorized，建立多代理端口隔离与稳定性保障体系。

### 案例背景
Orca 环境中 Hermes/Codex/Claude Code 三个 AI 系列并行运行，出现：
1. Codex 桌面版（Codex++）连接 MiMo API 返回 401 Unauthorized
2. Orca Mobile 刷新失败
3. 多个 MCP Client 启动报错（握手超时/解码失败）

### 龙虾五步法执行实录

#### Step 1 精准备份
- 操作：读取 ~/.codex/config.toml、项目 config.toml、~/.claude.json、orca-data.json 等全部配置
- 发现：Codex 桌面版 wire_api="responses" 直连 MiMo API，项目版 wire_api="chat" 走代理正常
- 产物：诊断报告（端口分配表、配置对比、进程状态）

#### Step 2 根因诊断
- 根因1：MiMo API 不支持 Responses API 格式，直连返回 401
- 根因2：Codex++ 管理工具会覆盖 ~/.codex/config.toml，手动修改无效
- 根因3：全域模板 #287.4 错误指导"代理端口为临时分配，应直连"
- 产物：故障链路图（Codex++ UI → config.toml → wire_api=responses → 401）

#### Step 3 无命令不执行
- 修复 ~/.codex/config.toml：wire_api="chat"、base_url=127.0.0.1:15730、model=mimo-v2.5-pro
- 验证 15730 代理返回 HTTP 200 + 正确模型列表
- 重启 Codex++ 桌面版
- 产物：修改后的配置文件 + API 测试结果

#### Step 4 验证修复
- Codex CLI（项目分支）：✓ 正常响应
- 15730 代理：✓ HTTP 200
- 15721 代理：✓ HTTP 200
- 健康检查脚本：✓ 所有关键检查通过
- Codex 桌面版：✗ 仍不正常（Codex++ UI 配置覆盖问题，需在 UI 中手动修改）
- 产物：scripts/fleet_health_check.sh 健康检查报告

#### Step 5 沉淀归档
- 创建快照：snapshots/fleet_snapshot_20260729_005023.tar.gz（48.3KB，脱敏）
- **升级代理 v6**：codex_tool_proxy.py 从 v5 升级到 v6
  - 路径：E:/龙虾AI主控中心/MCP服务/codex_tool_proxy.py
  - 新增功能：Responses API → Chat Completions 自动转换
  - 效果：Codex++ 桌面版用默认配置（wire_api=responses）即可正常工作
- 创建新快照：snapshots/fleet_snapshot_20260729_010700.tar.gz（50.9KB，含代理v6）
- 创建文档：docs/龙虾舰队多代理稳定性保障规范.md
- 更新全域模板：#287.4 端口适配修正（v3.112）
- 更新脚手架 README：v1.3 稳定性保障
- 更新记忆：Codex 桌面版配置陷阱 + 代理 v6
- 产物：快照 + 代理v6 + 规范文档 + 模板更新 + 健康检查脚本

### 关键教训
1. **代理层是必须的**：MiMo API 不兼容 Responses API，所有 Codex 必须走代理
2. **UI 管理工具会覆盖配置**：Codex++ 管理工具写 config.toml，手动修改会被覆盖
3. **解决方案：让代理适配客户端**：代理 v6 同时支持 Responses API + Chat Completions 双格式
4. **全域模板指导要准确**：错误的"直连"建议会导致系统性故障
5. **健康检查脚本化**：bash scripts/fleet_health_check.sh 一键诊断
6. **快照 ≤20MB**：脱敏后存项目 snapshots/，便于回滚
